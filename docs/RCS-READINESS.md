# RCS readiness: every place we assume a message is SMS-shaped

**Status: SPIKE OUTCOME (#230), 2026-08-02.** An inventory, not a plan. The
decision this feeds is `docs/DECISIONS.md` D111. No production behaviour
changed to produce it.

## What this answers

#230 asked one question: *is adding RCS later a change we make, or an
architecture we rewrite?* The way to answer it was to find every site that
assumes a message is 160 characters of text, counted in segments, delivered
rather than read, from a ten-digit number.

**36 sites. None of them XL.**

| Effort | Sites |
|---|---|
| S — under an hour | 9 |
| M — a few hours | 17 |
| L — a day | 10 |
| XL — multi-day/architectural | **0** |

That distribution is the finding. There is no site where the shape of the data
model forces a rewrite; the expensive ones are expensive because they are
*live billing surfaces*, not because they are structurally wrong.

## The one that gets worse with time

Everything below can be done when there is a reason to do it. **One cannot.**

`usage_events` has no channel dimension. Every outbound message the product has
ever billed is one of two SMS shapes measured in one unit, and the audit's own
words on it: *no backfill can reclassify rows that were never tagged.* Every
other item on this list stays the same price whether it is fixed today or in
two years. This one silently gets more expensive every day the ledger grows,
because the history it fails to record is unrecoverable.

That is tracked as #506 so it can be decided on its own merits rather than
waiting for RCS. It is not fixed here: this spike changes no production
behaviour, and a schema change is production.

## Three things the list makes obvious

**1. The billing sites are the hard ones, and they are hard for a commercial
reason rather than a technical one.** Splitting the Stripe meter (`meter.ts`)
is an L because it is a migration across live, already-billing subscriptions —
not because the code is complicated. Anything touching money on running
accounts costs more than the same change made before the first customer.

**2. The segment estimator is hand-ported three ways, and all three would be
wrong together.** `packages/shared/src/segments.ts` plus its Kotlin and Swift
twins tell a person what their message will cost before they send it. On a
channel that does not bill per segment, all three confidently show a number
that means nothing — and they would agree with each other while doing it, which
is the failure mode that survives review.

**3. The delivery ladder ends at `delivered`, on every layer at once.** The
enum, the status mapper, and the four-state `when`/`switch` in each client's
message bubble all stop there. RCS read receipts are not a new value in an
existing list; they are a promise the product does not currently make. Three
of the client sites close their branch with `else -> null`, so an unknown
status renders as nothing rather than as an error — which is the right failure
direction and worth keeping.

## What this list is not

It is not a migration plan, and nothing here should be read as scheduled work.
Several entries are only correctly *solvable* in an order — the cost constants
cannot be right before the ledger can record a channel, and the overage
arithmetic cannot be right before the meter it must agree with is split. Doing
them piecemeal in the order they appear would produce a period where the
numbers disagree with Stripe, which is worse than not starting.

See D111 for what would have to be true before any of it is worth doing.
